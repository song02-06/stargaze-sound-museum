# 数据库说明

> 依据：`code/backend/src/main/java/com/starmuseum/domain/` 下真实的实体映射。
> 表名、列名以实体注解为准；H2 里未加引号的标识符会变成**大写**，查询时不区分大小写。

数据库是 **H2 文件库**，连接串形如
`jdbc:h2:file:/srv/starmuseum/data/museum`（本机默认 `./data/museum`）。
`spring.jpa.hibernate.ddl-auto: update`，第一次启动自动建表。

老师没有指定必须 MySQL，所以本轮**不换数据库** —— H2 文件模式已经满足「前端 + 后端 + 数据库」
这条要求，而且在单实例部署下是持久化的。

## 一、七张表

| 表 | 实体 | 装什么 |
| --- | --- | --- |
| `museum_session` | `Session` | 轻身份：`device_key`、`nickname`。没有密码、没有邮箱 |
| `exhibit` | `Exhibit` | 用户投稿（一件展品）：声音、标题、展签、全文、地点、日期、分类、状态 |
| `echo` | `Echo` | 回音：文字或语音，挂在某件展品下面，自带审核状态 |
| `heritage_sound` | `HeritageSound` | 历史之声专区（当前是**合成演示的展位**，不是真实史料） |
| `draw_log` | `DrawLog` | 打捞记录：谁、什么时候、捞到了哪个类型的哪个对象 |
| `audit_record` | `AuditRecord` | 审核流水：每一路一条，带 `cost_ms`（论文实验的数据源） |
| `notification` | `Notification` | 消息：给谁的、什么类型、指向哪件展品、读没读 |

### exhibit（主要字段）

| 列 | 类型 | 说明 |
| --- | --- | --- |
| `id` | bigint 自增 | 主键 |
| `no` | varchar(8) 唯一 | 馆藏编号（`0247`）。**由数据库序列分配**，删号不重用 |
| `title` | varchar(80) | 用户写的标题 |
| `sign_text` | clob | 展签：从全文做减法得到，`SignGuard` 强制是全文的字符子序列 |
| `full_text` | clob | 全文（用户手写）。系统永不改写；用户主动编辑时可以更新 |
| `place` | varchar(60) | 地点 |
| `recorded_on` | date | 录制日期（不能是未来） |
| `audio_path` | varchar(200) | 相对 `museum.audio-root` 的路径，如 `exhibits/20261023_ab12cd34.wav` |
| `seconds` | int | 时长。**服务端从 WAV 头读出来**，不听客户端 |
| `trace` | clob | 波形点（逗号分隔，720 点） |
| `keeper_id` | bigint | 作者会话 id（普通字段，**不是数据库外键**） |
| `keeper_name` | varchar(12) | 投稿时的昵称快照 |
| `status` | varchar(12) | `PENDING` / `PASS` / `REVIEW` / `REJECT` |
| `audit_reason` | varchar(200) | 转人工或驳回的原因 |
| `sound_type` | varchar(16) | `ENVIRONMENT` / `SPEECH` / `SINGING`（演唱强制人工） |
| `original_confirmed` | boolean | 原创声明。写入时必须是 `true`，否则服务端拒收 |
| `created_at` | timestamp | 创建时间 |
| `updated_at` | timestamp | 最后一次用户编辑时间；没改过就是 `null` |
| `seeded` | boolean | 演示数据标记。界面按它显示「演示」角标 |

### echo

关键列：`exhibit_id`、`author_id`、`author_name`、`kind`（`TEXT`/`VOICE`）、`body`、`audio_path`、
`seconds`、`trace`、`status`、`audit_reason`、`created_at`、`seeded`。

- 语音回音的 `body` 是**转写文本**，没有配置真实 ASR 时它是 `null`
  （不会用样例句子冒充用户说的话）。
- 只有 `status = 'PASS'` 的回音出现在公开列表、收件箱和通知里。

### notification

| 列 | 说明 |
| --- | --- |
| `recipient_session_id` | 收消息的人 |
| `kind` | `ECHO_RECEIVED` / `EXHIBIT_REVIEW_RESULT` / `ECHO_REVIEW_RESULT` |
| `target_type` / `target_id` | 消息指向的对象（`EXHIBIT` + 展品 id） |
| `target_no` | 展品编号，前端靠它拼跳转 URL |
| `summary` | 一句人话（≤200 字） |
| `created_at` / `read_at` | 未读 = `read_at is null` |
| `target_gone` | 目标展品被删后置 true，消息不再出现在收件箱 |

### audit_record

`target_type` + `target_id` + `stage` + `verdict` + `detail` + `cost_ms` + `operator` + `created_at`。

- `stage`：`RULE`（规则路）、`MANUAL`（人工复审）、`ASR`（转写）、`SIGN`（展签压缩）。
- `stage = 'AI'` 保留在枚举里只是为了兼容老库里的历史数据；
  **现在的代码不会再写新的 AI 流水**，因为本项目没有接入真实大模型内容审核。

## 二、关系

```
museum_session ──1:N──▶ exhibit.keeper_id          （谁是投稿人）
museum_session ──1:N──▶ echo.author_id             （谁写了回音）
exhibit        ──1:N──▶ echo.exhibit_id            （回音挂在哪件展品下）
museum_session ──1:N──▶ notification.recipient_session_id
exhibit        ──1:N──▶ notification.target_id     （消息指向哪件展品）
audit_record   ──N:1──▶ exhibit / echo             （按 target_type + target_id）
draw_log       ──N:1──▶ exhibit / heritage_sound   （按 target_type + target_id）
```

⚠️ **除主键外，当前这些关联都是普通 ID 字段，没有建数据库级外键约束。**
ER 图上不能把它们画成「数据库已强制的外键」。应用层负责一致性
（比如删展品时在同一个事务里删回音、让消息失效）。

## 三、本轮新增的字段与序列（一次性步骤）

Hibernate `ddl-auto: update` **只加不改**。新列会被自动加上，但都是**可空**的，
所以老库不会有加列失败的问题：

| 新增 | 位置 | 老数据怎么读 |
| --- | --- | --- |
| `sound_type` | `exhibit` | 为 `null` 时按 `ENVIRONMENT` 处理 |
| `original_confirmed` | `exhibit` | 为 `null` 时按「未声明」处理 |
| `updated_at` | `exhibit` | `null` = 从没编辑过 |
| `notification` 表 | 新表 | 新建，无老数据 |
| 序列 `exhibit_no_seq` | H2 | 启动时自动创建并和 `max(no)` 对账 |

编号序列的初始化由 `config/ExhibitNoAllocator` 在启动时完成，等价于下面这几步：

```sql
-- 1）建序列，起点 = 现有最大编号 + 1（空库则 247）
CREATE SEQUENCE IF NOT EXISTS exhibit_no_seq START WITH 252 INCREMENT BY 1;

-- 2）和现有数据对账：序列落后就往前重启（只前进，不回退）
ALTER SEQUENCE exhibit_no_seq RESTART WITH 252;
```

> 既有编号**一律不重排**、不重新播种。删除最大编号之后新投稿**不会**重用那个号。
> 如果老库里有 `sound_type` 为空的行，想看整洁可以执行一次（可选）：
> ```sql
> UPDATE exhibit SET sound_type = 'ENVIRONMENT' WHERE sound_type IS NULL;
> UPDATE exhibit SET original_confirmed = FALSE WHERE original_confirmed IS NULL;
> ```

## 四、演示查询

验收时用来证明「数据库真的变了」：

```sql
-- 最近提交的展品（看 status 与编号）
SELECT id, no, title, keeper_id, status, sound_type FROM exhibit ORDER BY id DESC;

-- 回音与它的审核状态
SELECT id, exhibit_id, author_id, kind, status FROM echo ORDER BY id DESC;

-- 消息与已读状态
SELECT id, recipient_session_id, kind, target_no, read_at, target_gone
FROM notification ORDER BY id DESC;

-- 审核流水（含人工复审）
SELECT id, target_type, target_id, stage, verdict, cost_ms, detail
FROM audit_record ORDER BY id DESC;

-- 打捞记录（验证分类型去重）
SELECT id, session_id, target_type, target_id FROM draw_log ORDER BY id DESC;

-- 演示数据 vs 真实投稿
SELECT no, title, seeded FROM exhibit ORDER BY no;
```

打开方式（本机，Node 与 Maven 之外只用一个 jar）：

```bash
cd code/backend
mvn dependency:copy-dependencies -DoutputDirectory=target/lib -q
java -cp target/lib/h2-*.jar org.h2.tools.Shell \
  -url "jdbc:h2:file:./data/museum" -user sa -password ""
```

生产环境请用受控连接，**不要为了验收公开一个数据库管理页面**。

## 五、备份与恢复

数据库和音频是**两样东西**，必须一起备份、一起恢复：

```bash
# 停服务（H2 文件模式不要在写入过程中拷文件）
sudo systemctl stop starmuseum

# 一起打包：库里存的是音频的**相对路径**，只恢复其中一个都会对不上
sudo tar czf /var/backups/starmuseum-$(date +%F).tar.gz \
  -C /srv/starmuseum data

sudo systemctl start starmuseum
```

恢复：停服务 → 解开到 `/srv/starmuseum/data` → 确认属主是 `starmuseum` → 起服务。
**只复制 `museum.mv.db` 而不复制 `audio/`，页面会有数据但播放 404。**
