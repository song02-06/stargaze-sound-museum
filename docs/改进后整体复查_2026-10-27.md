## 一、应优先修复的问题

### 1. 部署目录权限会阻止 Caddy 提供前端页面（P1）

位置：`docs/部署说明.md:38–39`、`:90–101`，`deploy/Caddyfile` 的站点根目录。

文档将 `/srv/starmuseum` 属主设为 `starmuseum:starmuseum`，权限设为 `750`，而 Caddy 要从该目录下面的 `web` 读取文件。按文档使用标准独立 Caddy 服务用户，且没有额外组或 ACL 配置时，Caddy 无法穿过父目录，首页及全部静态资源会被拒绝访问。文档中的普通 SSH 用户 `scp` 直传 app/web/data 也没有被授予写入权限。

最小修改：明确采用临时上传目录再 sudo 安装文件的流程；给 Caddy 对父目录的遍历权限以及对 web 的读取权限，保留 data 的访问限制。不能只修改 web 子目录权限，因为父目录仍会拦住访问。本项为部署步骤静态推导，未在 Linux 服务器实测。

### 2. 未通过审核的展品仍可读写公开回音（P1）

位置：`code2.0/backend/src/main/java/com/starmuseum/web/EchoController.java:35–36`、`:51–54`。

GET/POST 回音都只调用 `exhibitService.require`，该方法只判断记录存在，不判断 PASS。与之相对，展品详情接口会拒绝未通过的展品。

正常触发：B 已打开某展品的回音页，A 随后编辑该展品，令它进入 REVIEW/REJECT。B 的旧页面仍会继续轮询 PASS 回音，也仍可发送新的回音；甚至产生“已送达”通知，而展品公开详情已经打不开。这是编辑重审的正常可达流程，不需要恶意构造。

最小修改：公共回音 GET/POST 必须要求所属展品为 PASS。作者管理和管理员审核入口维持各自权限与用途。前端遇到下架响应应提示该展品正在重审，并停止发送。

### 3. 编辑投稿会覆盖原音频引发的隐私复审（P1，启用真实 ASR 时）

位置：`code2.0/backend/src/main/java/com/starmuseum/service/ExhibitService.java:255–264`、`:335` 起的 `checkAudioPrivacy`。

创建投稿时，真实 ASR 若识别到隐私内容，会把展品置为 REVIEW；创建逻辑刻意保留该结论。但编辑不更换音频，也不重新处理音频结论，只对新文字审核，再调用 `applyOutcome(..., false)`。普通文字通过就直接 `approve()`，使原来因音频隐私而待审的同一音频自动入馆。

正常触发：真实 ASR 将某环境声/说话投稿转隐私复审，作者只改标题或故事，再保存。音频没变，却绕开了原本需要人工听审的决定。

最小修改：编辑时重新执行原音频检查并合并文字结论，或明确保留尚未人工解决的音频复审原因。不要无条件保留所有 REVIEW，因为文字原因本来就允许作者修改消除。本次未调用真实 ASR，结论来自创建和编辑控制流差异。

### 4. 投稿的 mock ASR 仍被记录为隐私识别通过（P2）

位置：同上 `ExhibitService.java:335–350`，及 `asr/MockAsrClient.java`。

回音流程已经正确用 `asr.reliable()` 避开伪转写；投稿隐私检查却仍直接调用 mock 的 `transcribe()`。默认配置下，每次投稿都会拿随机样例文本扫描隐私，并记录 ASR PASS、“转写若干字”。operator 虽标为 `asr:mock`，但这个 PASS 仍不能证明原音频经过识别或隐私检查。

最小修改：投稿端也检查 reliable；未配置真实 ASR 时如实记录“未执行音频隐私检查”。是否仍允许普通投稿按文字规则入馆可沿用产品现状，不必为了这个问题一律转人工。应修正的是记录和能力表述。

## 二、用户流程仍有的问题

### 5. 驳回消息跳到必然打不开的公共详情页（P2）

位置：`code2.0/frontend/src/views/MineView.vue:243–253`，及 `ExhibitController.java` 的详情状态判断。

所有消息只要有 targetNo，就跳 `/exhibit/{no}`。管理员驳回投稿后，作者点“未通过”消息，也会走公共详情；该接口对 REJECT 明确返回 404。作者虽然有权在编辑页看到自己的原投稿，却被带到了错误入口。旧的通过/回音消息在展品再次进入重审后也会遇到同类问题。

最小修改：作者的投稿审核结果进入本人投稿管理/编辑页；公开回音消息依据当前可见状态进入详情或显示暂不可访问。不要通过放开公共详情访问未审核内容来修复跳转。

### 6. 回音被驳回时仍清空草稿（P2）

位置：`code2.0/frontend/src/views/EchoView.vue:120–122`，`components/EchoComposer.vue` 的 resetToken 监听。

服务端业务驳回返回成功响应及 `status=REJECT`。父组件收到任何成功响应都会递增 resetToken，清空文字、语音和试听资源。界面却提示“看看原因，改一改再发一次”，组件注释也承诺“被驳回时内容必须还在”。因此 HTTP 失败保留草稿已经实现，但业务驳回保留草稿没有实现。

最小修改：仅在 PASS/REVIEW 等已接收状态清空；REJECT 保留输入供修改。验证时要覆盖业务 REJECT，不能只模拟网络失败。

### 7. 收件箱看不到回音属于哪件展品（P2）

位置：`code2.0/frontend/src/views/MineView.vue:69`、`:215`，`components/EchoList.vue:6–36`。

后端 InboxEcho 已返回 exhibitNo 和 exhibitTitle，页面直接复用只显示作者、时间、正文/播放器的 EchoList，没有显示目标展品或提供跳转。作者拥有两件以上投稿时，无法从收件箱判断一条回音回应的是哪件声音。默认演示可能只有一件投稿，因此容易漏看。

最小修改：在收件箱条目增加展品标题、编号和链接，或按展品分组；无需重做整个回音组件。

### 8. “我的声音”首次失败后重试成功，不会开启页面轮询（P2）

位置：`code2.0/frontend/src/views/MineView.vue:37`、`:190` 起的 load、`:229–239`。

页面只在 onMounted 首次 load 成功时调用 start。首次因后端未启动或网络失败时不启动轮询；用户点击重试调用的只是 load，成功后也没有调用 start。页面虽然恢复显示，投稿状态、收件箱和消息却不会再自动更新。顶栏独立轮询不能代替页面内容刷新。

最小修改：让成功重试也能启动轮询，统一首载与恢复路径，避免重复挂监听。

## 三、验收交付仍缺什么

这些不是凭空新增的要求，而是原报告尚未完成的交付项：

1. **公网部署与双网络实测**：当前部署材料仍使用示例域名，实施报告明确未部署。完成文件不等于已经满足“不同网络可访问”。应在修正权限步骤后完成 HTTPS、深层路由、音频拖动、手机录音和服务重启持久化实测。
2. **真实音频素材**：仍以合成占位素材为主。标注为演示是正确的；但要展示“声音博物馆”的内容价值，仍应准备原报告要求的 3–5 段本人授权真实录音与故事。
3. **成员贡献与最终代码版本**：团队贡献表姓名、账号和链接仍待填，本地大量新增文件未被 Git 跟踪。应由各成员提交实际工作，核对远程与本地差异后确定验收分支。本次未查询远程，不能断言远程最新状态，也不应直接强推对齐。

真实大模型审核不是本轮必须补的功能；默认语音回音转人工且管理端可听，是合理的实现。H2、轻身份与五秒轮询也符合本项目规模，不列为缺陷。
