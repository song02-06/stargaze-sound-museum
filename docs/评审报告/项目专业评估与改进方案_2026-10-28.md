# 星轨 · 声音博物馆：专业评估与改进方案

评估日期：2026-10-28。对象：当前工作区正式主线 `code2.0`，包含尚未提交的改动。本文交付改进方案，没有修改业务代码、正式数据库或部署配置。

## 一、整体判断

**项目已经具备完整原型的骨架，下一步应该把“有人愿意听、愿意留下声音、能收到回应”做扎实。**

目前最有价值的部分是“声音、故事、时间地点、陌生人的回音”构成的体验。深空、黄铜、宋体和历史展位的纸张视觉已经形成一致的表达，值得保留。投稿、编辑重审、删除、馆藏检索、消息与人工复审也已有真实实现，继续开发有可靠基础。

当前主要差距有三类：

1. **内容价值尚未得到证明。** 随项目提供的馆藏仍是合成占位音频；文字讲述了便利店、雨、老井，声音还没有真正承载这些故事。
2. **常规流程仍有断点。** 审核状态改变后，公开回音、通知跳转、输入保留和自动刷新没有完全接上。
3. **声音保存与手机使用还可提升。** 展品音频统一转为 16kHz 单声道，录音默认降噪；投稿离开页面后丢失输入，部分操作文字也偏小。

建议按“流程正确与真实内容 → 声音质量与操作体验 → 试用和交付”的顺序推进。

### 已经做对的部分

- **范围控制合理。** Vue + Spring Boot 单体、H2、本地设备身份、五秒轮询适合当前项目规模。没有证据要求换库、上微服务或引入复杂账号系统。
- **交互与产品理念一致。** 真实波形随播放高亮，展签与全文切换，背景星空静态绘制，减少动态效果有对应处理。
- **能力边界有如实说明。** 演示角标、合成素材说明、规则审核与人工复审的区分是正确的；默认语音回音转人工也是合理选择。投稿端的 ASR 流水仍有一处例外，见下文。
- **已有有效验证。** 本次前端构建成功；后端 78 项测试全部通过，0 失败、0 错误、0 跳过。首包主 JS 构建输出约 114.26kB、gzip 44.80kB，路由已拆包，没有依据把“大规模性能重构”列为首要工作。

## 二、先修复这些明确问题

以下结论均重新对照了当前代码。与 10 月 27 日旧报告重合的项目，是因为当前实现中仍存在对应控制流，不是直接照搬历史结论。

P1 表示应在下一次正式演示或交付前修复；P2 表示明显影响体验，应安排在紧接着的一轮。它们是执行顺序，不是项目评分。

### A. 审核状态与公开行为保持一致（P1）

**问题一：展品进入重审后，原回音页仍可读写公开回音。**

`EchoController.java:35、52` 调用的 `exhibitService.require()` 只要求展品存在；公开详情接口则要求状态为 PASS。正常场景是：听众已经打开回音页，作者随后编辑展品使其进入 REVIEW/REJECT，旧页面仍然可以获取回音、发送新回音。

改法：公共回音 GET/POST 与公共详情使用相同的可见条件；前端收到不可访问结果后说明“这段声音正在重新审核，暂时不能留下回音”，保留正在编辑的内容。作者编辑和管理员复审继续使用各自入口。

验收：打开听众回音页，再由作者把所属展品改为待审；旧页面不能再公开读取或新增回音，重新通过后恢复正常。

**问题二：编辑文字会覆盖音频引发的隐私复审。启用真实 ASR 时可触发。**

`ExhibitService.java:221–226` 在创建时保留音频检查产生的 REVIEW；编辑路径 `:255–264` 没有重新检查音频，也没有保留尚未处理的音频结论，文字通过即可批准同一音频。

改法：保存编辑时合并文字和音频结论。最直接的首期方案是重新检查原音频，再合并状态；若以后 ASR 成本确实明显，再保存并复用已有音频结论。文字修改能消除的复审原因应允许解除，音频原因则必须得到对应处理。

验收：用可控 ASR 测试替身返回含隐私的信息，创建后为 REVIEW；仅修改普通标题、故事后，仍需人工处理该音频。无需为这项回归测试调用收费识别服务。

### B. 审核记录只记录实际执行的能力（P2）

`ExhibitService.java:335` 无条件调用 ASR；默认 `MockAsrClient` 返回样例文本及成功结果，于是投稿流水会出现 ASR PASS、“转写若干字”。语音回音已经通过 `asr.reliable()` 避开这一问题，投稿路径尚未对齐。

改法：投稿端同样识别 mock；记录“未执行真实音频识别/隐私检查”，不把样例文本计作识别结果。普通投稿是否继续按文字规则入馆可沿用现有产品约定。

验收：默认 mock 投稿不再出现能够被误读为真实音频识别通过的记录；真实识别失败、成功及命中隐私的流水能区分。

### C. 修复回音与“我的声音”的衔接（P2）

| 当前问题与证据 | 最小改进 | 完成标准 |
| --- | --- | --- |
| `EchoView.vue:120–122` 收到任何成功 HTTP 响应都增加 `resetToken`；业务状态 REJECT 也会清掉文字和语音 | 仅在已接受投稿的状态清空；REJECT 保留输入并展示原因 | 业务驳回与网络失败后都能直接修改重发，已接受的回音正常清空 |
| `MineView.vue:243–253` 所有消息都跳公共详情；被驳回投稿的详情必然无法公开访问 | 投稿审核结果进入本人投稿管理/编辑入口；公开回音消息根据目标当前状态处理 | 作者点“没通过”后能看到原因并修改，不落到错误页面 |
| `MineView.vue:69、215` 的收件箱复用 `EchoList`，没有显示后端已返回的展品编号和标题 | 在收件箱条目加目标展品及入口，保留现有回音排版 | 同一作者有两件以上投稿时，每条回音都能明确对应展品 |
| `MineView.vue:230–238` 只在首次加载成功时启动轮询；首次失败后点重试只执行 `load` | 把首载与成功重试的轮询启动接到同一成功路径 | 服务暂不可用后恢复，重试成功仍能自动看到后续审核结果 |

这几项应合并成一个“审核结果能被作者理解并继续操作”的工作包，避免每页单独修一点却没有完整走通。

### D. 修正两个时间口径问题（P2，顺手完成）

- **首页把录制时间写成入馆时间。** `HomeView.vue:43` 使用 `item.date` 计算“几个月前入馆”；`ExhibitService.toCard():121` 返回的却是 `recordedOn`。今天投稿一段去年录的声音，也会显示去年入馆。最小改法是显示“录于某日”；若要表达入馆时间，应明确按首次公开时间提供字段。
- **日期表单按 UTC 生成“今天”。** `BuryView.vue:261、264` 和 `EditUploadView.vue:153` 使用 `toISOString().slice(0, 10)`。在北京时间 00:00–07:59 会得到前一天，连当天的录制日期也可能被 `max` 限制。按产品使用时区生成日期，并使服务端“不可为未来”判断使用相同口径即可。验收用北京时间凌晨的固定时间，确认当天可选；这不是毫秒竞态问题。

### E. 修正部署步骤中的实际阻碍（P1，执行上线前）

`docs/部署说明.md:38–39` 把 `/srv/starmuseum` 设为 `starmuseum` 所有、权限 750；标准独立 Caddy 用户不能穿过这个父目录读取 `web`。`:90–101` 的普通 SSH 用户直传 app/web/data 也没有相应写入权限说明。

改法：文档明确“先上传到 SSH 用户临时目录，再 sudo 安装”的步骤；给 Caddy 对父目录的遍历权限和对 web 的读取权限，data 继续由应用持有。无需扩大为权限系统重构。

验收：按文档从一次干净部署完成首页、深层路由、API 和音频访问，并由 Caddy 的实际服务用户确认文件可读。此项来自部署步骤静态推导，本次未操作 Linux 服务器。

## 三、产品体验的重点改进

### 1. 用真实录音建立项目的内容价值

**建议与第一阶段修复同时开始，这是最能改变观感的一项。**

当前 [素材来源登记](../素材来源.md) 明确馆藏为脚本生成的占位音频，实时页面也能看到“合成演示”标记。标注已经做对，但真实声音与真实故事的对应关系仍需要补齐。

首期制作 **5 件真实声音展品**，由团队本人录制并通过正式投稿流程入库。可从雨声、家中旧物、街边环境、个人讲述、原创演唱中选择；演唱照现有规则人工复审。每件保留原始录音、真实日期、模糊地点、本人故事和来源/使用确认。

再邀请两三位实际参与者为其中的展品留下真实回音，至少完成一条语音回音的“提交 → 人工听审 → 公开 → 作者收到提示”流程。不要把团队试用描述成自然用户增长。

历史展位继续明确标注为示例；有可靠来源与使用依据后再替换为真实素材。首期先把日常声音做完整。

完成标准：观众打开任意一件重点演示展品，都能听到与故事对应的真实内容；演示数据与实际投稿能区分。

### 2. 调整声音链路，让保存质量符合“声音博物馆”的定位

`frontend/src/lib/audio.js:6、24、72–90` 表明，现场录音与导入文件都会转为 **16kHz 单声道 WAV**，现场采集还统一请求回声消除和降噪。这个取舍方便当前 ASR，但也让展品播放只能使用同一份处理后的音频。

这是产品质量改进，不代表现有声音无法播放，也没有在本次实测出某台手机具体损失了多少细节。特别是环境声，开启降噪可能削弱原本想保存的背景声音；浏览器及设备是否执行、执行程度如何，需要真实录音对比。[MDN 对降噪约束的说明](https://developer.mozilla.org/en-US/docs/Web/API/MediaTrackConstraints/noiseSuppression)支持这一技术判断。

建议：

- **区分展品播放与语音识别的用途。** 展品首期可保存 44.1/48kHz、16 位、单声道 PCM；ASR 仍使用当前需要的 16kHz 副本。不要只提高上传采样率，却继续把原文件按 16kHz 声明交给 `BaiduAsrClient`。
- **按现有声音分类采集。** 把分类选择移到录音前；环境声优先保留环境细节，说话和语音回音可沿用人声处理。浏览器不支持某个约束时按实际能力录制，不承诺所有设备效果一致。
- **控制首期范围。** 先不引入多格式转码平台、母带管理或立体声链路。48kHz 单声道 60 秒的 PCM 数据约 5.76MB，适合现有单文件 8MB 限制；识别副本只在需要时生成并清理。

完成标准：同一段真实雨声/街声与讲述分别通过手机录制、文件导入测试；对比输入和最终播放，确认目标采样率、时长与波形正确，ASR 的输入格式没有被破坏。

### 3. 保留已经投入的输入，减少投稿挫败

本次在运行中的投稿页输入标题和故事，进入馆藏再返回投稿页，输入已清空。`BuryView`、`EditUploadView` 与 `EchoComposer` 主要持有组件内状态，也没有完整的草稿恢复流程。

首期方案：

- 投稿和编辑页保留本机文字草稿，包含标题、故事、地点、日期、分类；重新进入时允许继续或丢弃。
- 已录制但未提交的音频，离开时明确提醒；首期无需为了草稿另建服务端数据表。若后续试用证明录音恢复是主要需求，再增加本机音频保存。
- 请求失败、业务驳回保留输入；真正提交被接受后清理对应草稿。
- 选入超过 60 秒的音频时立即说明时长限制。当前 `canSubmit` 只检查最短时长，长文件仍可走到服务器拒绝；先补明确提示与阻止提交，无需立刻开发音频剪辑器。

完成标准：正常切换页面或刷新后，文字可以恢复；音频不会在无提示的页面离开中被丢弃；超长文件在提交前说明原因。

### 4. 让第一次来的用户更容易开始

首页现在主要表达“有多少段声音”，两个按钮均使用主按钮样式。视觉很安静，但“打捞”“埋下”的隐喻需要用户自行理解。

建议保留现有构图，只做三点调整：

1. 增加一句短说明，例如“听一段陌生人的声音，也留下一段自己的生活”。
2. 把“打捞一段”作为首次来访的主要动作，补“随机听一段”的解释；“埋下一段”保留入口并说明 10–60 秒。
3. “最近入馆”卡片补时长和清晰的演示标记，让用户知道点进去会听多久、内容是什么。

不要新增强制 onboarding 弹窗。用首页自身解释即可。

完成标准：找 5 位未参与开发的人，观察能否不经讲解就开始听声音，并理解如何投稿；记录卡住的位置，不把小样本结果写成统计性结论。

### 5. 改善手机上的阅读和播放操作

本次实时查看了窄屏首页、馆藏、普通展品、历史展位和投稿页。布局已有响应式处理，主要改进空间是阅读与操作层次：

- `AppTopBar.vue:81` 的移动导航、`ExhibitPlaque.vue:90` 的全文按钮为 11px。建议把常用功能文字提高到约 13–14px，主要阅读文字保持 15–16px，并给按钮足够的可点击区域。这是体验建议，本次未据此宣称通过或不通过完整无障碍标准。
- 展品页中波形、故事、播放操作距离较远，较矮的窗口里“留下回音”可能落到首屏之外。手机上优先缩短不必要留白，把播放与回音入口放到容易找到的位置；保留桌面的展览感。
- 自动播放受阻时，在波形附近显示明确的“点一下播放”。现有 `usePlayer` 已有 `blocked` 状态，可以直接使用。浏览器会限制有声自动播放，不能把自动出声作为唯一入口。[MDN 自动播放指南](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)说明了这一限制。
- **当前多个播放器缺少互斥。** 回音页的展品播放器、`EchoList` 内部的 `new Audio()` 和录音试听分别管理，启动后者只暂停各自旧实例。正常连续点击会出现同时播放的路径。让当前页面开始一段声音时暂停其他活动声音即可，无需开发播放队列。
- 投稿页删去“分类会存进数据库”“这一勾会随投稿存进数据库”等实现说明，改成审核影响、原创要求和等待方式。我的声音页也应解释设备身份及记录保留方式，避免“没人知道你是谁”这类绝对表述。

完成标准：手机上能直接找到播放/暂停和留下回音；播放展品、语音回音或试听时，同一时刻只有一条内容声音；拒绝自动播放也能继续使用。

### 6. 内容稍多之后再完善浏览

现有关键词检索已经有价值。等真实展品达到约十几件，可把现有“环境声/说话/演唱”做成馆藏筛选，卡片补时长。规模仍小时不用引入推荐算法、标签运营后台或搜索服务。

“回应过的展品”与公开回音已经能承担重访入口；先观察试用者是否真的找不到听过的内容，再决定是否增加收听历史或收藏。产品文档里的“按标签与新奇度”当前尚未实现，应标为后续意图，避免读者误认为已有功能。

## 四、建议实施安排

以下为熟悉项目的一名开发者的粗略工作量估计，包含对应验证；素材采集、参与者和服务器准备会影响日历时间。

| 阶段 | 工作内容 | 预计投入 | 阶段成果 |
| --- | --- | --- | --- |
| 第一阶段：流程与内容 | 修复第二节 A/B/C；同步准备 5 件真实录音与回音；修正时间口径 | 开发约 2–3 人日；素材并行准备 | 审核状态、通知、回音、草稿清理行为正确；有可完整演示的真实内容 |
| 第二阶段：声音与手机体验 | 播放/识别用途区分、环境声参数；文字草稿；超长文件提示；播放器互斥；首页说明及常用操作调整 | 约 3–5 人日 | 声音质量与输入保护更可靠，手机用户能独立完成主要任务 |
| 第三阶段：试用与交付 | 修部署步骤；真实 HTTPS 环境；手机及跨网络使用；修试用中影响完成任务的问题；整理版本与材料 | 约 1–2 人日，依赖服务器和域名就绪 | 可访问的演示地址、一次完整跨角色演示、可复现的交付版本 |

**若只剩两三天：优先 A/C 的流程修复、mock 流水纠正、真实录音和演示路径；需要上线就同时修部署说明。** 声音质量调整不应仓促只改一端，宁可完整放到下一轮。启用真实 ASR 时，A 中的音频复审问题必须随之修复。

视频动效方案可以保留。现有 2.4 秒打捞已能表达仪式感，在真实内容与上述流程完成后，再判断视频是否能带来值得其制作和加载成本的提升。

## 五、怎么判断这一轮已经完成

验证只覆盖会改变交付判断的失败，不做无止境复查。

| 验证 | 要发现的具体失败 | 失败后怎么处理 |
