## 四、最终项目范围：一次做完哪些事情

### 4.1 用户端

保留当前视觉和主要交互，完整支持：

1. 浏览馆藏、查看详情、播放音频、随机打捞。
2. 录制或上传 10–60 秒声音，填写标题、故事、地点和日期，勾选原创声明。
3. 在“我的声音”看到全部投稿及审核原因，编辑原投稿并重新审核，删除投稿。
4. 给已公开展品发送文字或 10–30 秒语音回音，看到提交结果和自己的审核状态。
5. 在“回音收件箱”看到自己的展品收到的公开回音，并收到审核结果通知和未读提示。
6. 馆藏支持按标题、故事或地点关键词检索，能够清空条件和显示无结果。

### 4.2 管理端

1. 管理口令进入 /admin。
2. 自动更新待复审数量与队列。
3. 看完整文字，**能播放展品和语音回音原音频**。
4. 通过或驳回，驳回必须有原因。
5. 查看审核流水，结果反馈给投稿人或回音发送人。

### 4.3 工程交付

1. 只维护 code2.0 作为正式运行入口。
2. 提供明确的构建、运行、部署、备份和恢复说明。
3. 一个公网 HTTPS 地址，用户端和管理端连接同一个后端。
4. 每名成员有可对应代码、PR 和职责的真实提交。
5. 验收文档给出前端操作、后端接口、数据库变化三者之间的对应关系。

本轮不要求微服务、Redis、消息队列、复杂登录系统、支付、私信、楼中楼或原生 App。保留现有轻身份与管理口令，按合作式课程演示场景完成业务。不要把“完整项目”扩写成商业平台重构。

## 五、必须实施的业务修改

以下路径均相对于项目根目录。P0 表示直接影响老师的验收主线，P1 表示影响正常使用和连续演示，均应纳入本轮；P2 为主线完成后的小幅补充。

### P0-1：补齐“编辑自己的投稿”，而不是再次新建

**事实依据：**

- backend 的 ExhibitController.java 目前有 GET、POST、DELETE，没有编辑展品的 PUT/PATCH。
- ExhibitService.java 有 create 和 delete，没有 update。
- MineView.vue 只有删除入口。
- BuryView.vue 的“回去改一改”仍然调用 uploadExhibit，实际再次 POST，产生新记录，不是在修改原投稿。

**修改方法：**

1. 新增 GET /api/mine/uploads/{no}，只允许原作者读取自己的编辑数据，包括待审和驳回内容。不要让公共详情接口直接公开未通过内容。
2. 新增 PATCH /api/exhibits/{no}，请求为 JSON，只编辑 title、full、place、recordedOn 和后文新增的投稿分类/声明字段。本轮编辑不必支持替换音频。
3. 在 ExhibitService 中实现 update，复用当前字数、日期等校验；保持 id、no、keeperId、audioPath、createdAt 不变，增加 updatedAt。
4. 修改故事后重新生成展签，并重新执行审核；标题、地点也必须审核，不能只检查全文。涉及新分类的人工复审条件也重新判断。
5. 更新后用现有 PENDING/PASS/REVIEW/REJECT 表示结果。转人工或驳回的内容暂时从公共馆藏、打捞和公共回音入口隐藏，原作者仍可管理。
6. 增加 /mine/uploads/:no/edit 页面，尽量复用投稿表单字段与样式。BuryView 在已有编号时进入编辑流程，不能偷偷再次 POST。
7. “全文保留”解释为不被展签覆盖；用户主动编辑可以更新全文。本轮不用引入版本管理系统，但要在产品文档写清此约定。

**完成证据：** 前端修改同一件展品标题和故事后，数据库相同 id/no 的字段变化，记录数不增加；页面刷新仍是新内容。其他会话不能编辑该投稿。

### P0-2：实现跨端送达的回音收件箱与通知

**事实依据：**

- MineController.java:27 返回 session、kept、echoCount、uploads。其中 kept 是“我回应过的展品”，不是“别人回应我的声音”。
- EchoRepository 没有作者收到的回音汇总查询，项目没有通知实体和通知接口。
- AdminView、MineView、EchoView 目前没有定时取数。已打开的页面通常要重新进入或手工刷新才看到外部变化。

**采用一个简单且明确的方案：数据库通知 + 每 5 秒轮询。** 当前任务没有必要同时实现 WebSocket、SSE 和轮询三套机制。

**新增数据与接口：**

| 内容 | 具体要求 |
| --- | --- |
| notification 表 | id、recipientSessionId、kind、targetType、targetId、summary、createdAt、readAt |
| kind | 至少 ECHO_RECEIVED、EXHIBIT_REVIEW_RESULT、ECHO_REVIEW_RESULT |
| GET /api/mine/inbox | 查询自己拥有的、当前已公开展品收到的 PASS 回音；返回展品编号、标题、回音内容/音频、作者、时间 |
| GET /api/mine/notifications | 返回自己的消息列表及未读数量；可采用简单分页 |
| PATCH /api/mine/notifications/{id}/read | 标记本人消息已读，只允许接收人操作 |
| 前端入口 | 顶栏未读点或数字、“我的声音”中的回音收件箱与审核消息 |

**事件发生时怎么做：**

1. 新投稿进入 REVIEW：管理端下一次轮询出现记录和数量变化。
2. 管理员审核投稿：在同一数据库事务中保存状态、人工审核流水和作者通知。
3. 普通用户给别人的展品发送回音：只有最终进入 PASS 时才通知展品作者；REVIEW/REJECT 不能当作公开送达。
4. 语音回音由 REVIEW 人工转 PASS 时，创建作者收到的回音通知，同时反馈发送人审核结果。
5. 审核入口按“状态发生变化”处理，不对同一次已完成审核反复生成通知；对已不在待复审状态的旧队列项提示刷新。
6. 本人给自己的展品回音，不需要给本人重复发送一份“别人回复你”的提醒。
7. 删除展品时，删除或失效处理其导航通知；不要留一个必然点不开的消息入口。
8. 收件箱仍然是公开回音的汇总，不改变当前“没有私信”的产品定义。

**前端轮询规则：**

- 只在需要的页面更新相关数据；顶栏可定时更新未读数量。
- 使用上次请求完成后再延时的方式，避免请求叠加；卸载页面时清理定时器。
- 标签页恢复可见时补一次刷新；断网时保留已显示内容，给出重试提示。
- 作者的投稿状态、管理端队列、展品回音列表都应能在正常前台使用时自动更新。

**完成证据：** A 浏览器投稿，C 管理端不刷新整页能看到队列；C 通过后 A 看到结果；B 用另一浏览器或手机回音，A 在约 5–8 秒内看到未读消息，点击进入对应展品。通知刷新后仍存在，标记已读后未读数减少。

### P1-1：修正回音“发了但不知道结果”和发送失败丢内容

**事实依据：**

- Dtos.java:41 的 EchoView 没有 status、auditNote 或 authorId。
- EchoController.create 无论审核通过、转人工还是驳回，都返回不带状态的 EchoView。
- EchoView.vue:82 提交后只重新加载 PASS 列表，不显示提交审核结论。
- EchoComposer.vue:153 的 sendText 发事件后马上 resetText；sendVoice 同样立即清空 take。网络失败也会丢失草稿或录音。
- 回车调用 sendText 时，函数本身没有判断 busy，按钮禁用不能阻止该路径重复提交。
- EchoList.vue:10 通过昵称判断“你写的”；系统默认昵称只有八种，正常用户会重名，改名后自己的旧回音也不再匹配。

**修改方法：**

1. 创建响应增加 status、auditNote。公共回音列表可保留精简 DTO，作者自己的回音管理结果要包含状态。
2. 在“我的声音”增加“我发出的回音”查询/视图，至少能看到待复审和驳回原因。
3. PASS 明确提示已公开；REVIEW 提示等待人工；REJECT 显示原因并保留可修改内容。
4. 改为父组件拿到成功结果后通知输入组件处理草稿。请求失败或被驳回保留文字和录音，已提交待复审的内容要给出编号或管理入口。
5. 点击、回车和语音发送都在函数入口判断 busy；不要只禁用按钮。
6. 用 authorId 与当前 session.id 比较身份，或由后端返回 isMine。不能使用昵称承担身份判断。
7. 保留录音时可以继续试听/重试；成功移除录音时停止试听并释放对象 URL。

**完成证据：** 模拟断网发送，内容仍在；恢复网络能重试。触发待审/驳回时能看到原因。两个相同昵称用户不会互相被标成“你写的”。

### P1-2：管理端必须能听取待审音频

**事实依据：** Dtos.java:51 的 PendingItem 只有文字信息；AdminController.java:40 的队列没有音频 URL；AdminView.vue 没有音频播放器。但 EchoService 已明确将 ASR 失败的语音送人工，因此会真实出现“必须人工听，却没有播放入口”的队列项。

**修改方法：**

1. 给 PendingItem 增加 kind、audioUrl、seconds；展品队列增加地点和录制日期，方便判断语境。
2. 管理页对有音频的项显示原生 audio controls 或现有播放器，允许无转写文本时直接试听。
3. 显示转写失败原因，但不要把失败原因当作音频内容。
4. 前后端都要求驳回理由非空、长度受限；管理决定调用清晰的服务方法，事务内同步写审核流水和通知。
5. 管理端能播待审音频，公开展品和回音接口仍只展示已通过内容。

**完成证据：** 故意让一次语音识别失败，回音进入 REVIEW；管理员能播放真实上传的声音，填写理由完成复审，发送人看到结果。

### P1-3：审核行为与页面承诺一致

**事实依据：**

- ExhibitService.java:156 只审核 cleanFull，公开标题和地点没有进入文字审核。
- BuryView.vue 明示“演唱类会转人工复审”，但上传没有演唱分类字段，后端也没有相应分支。
- 原创声明只在前端 agreed 控制按钮，没有传到后端保存。
- AuditService.java:60–61 的所谓 AI 路是直接写入“mock 判定：safe”；配置 ai-provider 目前没有切换真实审核的作用。
- MockAsrClient 随机返回样例句子，不是真的识别上传音频。
- 语音回音 ASR 失败转人工的逻辑**已经正确存在**，不能再当成未实现任务。

**本轮明确采用的完成方案：**

1. 投稿增加 soundType，至少 ENVIRONMENT、SPEECH、SINGING。前端由投稿者选择，后端校验和保存；SINGING 强制人工复审，不依赖自动识别演唱。
2. 增加 originalConfirmed 布尔字段，后端收到 false/缺失时拒绝提交，数据库保存声明结果。
3. 标题、故事、地点分别进入文字规则审核，合并结论时 REJECT 高于 REVIEW，高于 PASS，并保留具体原因。
4. 本轮以“本地规则 + 人工复审”为必须可靠的审核能力；**不要求额外开发一套真实大模型内容审核**。删除或改正“改一个 ai-provider 配置就能启用真实 AI 审核”的说明，不把无实际调用的 safe 当成真实审核结果。
5. 服务器若开启语音转写，使用已有 BaiduAsrClient，并用真人录音验证识别文本确实对应音频。只在服务器配置密钥。
6. 未配真实 ASR 时，语音回音进入人工复审，不能拿随机样例句当作该用户说的话并据此放行。Mock 可保留给现有自动测试和明确标注的演示。
7. 展品音频已有 ASR 失败不阻断投稿的产品策略，本轮不无故扩大成全部失败拒收；演唱分类和用户填写字段按上面规则处理。
8. 展签默认保留本地压缩器；真实远程压缩是加分能力，不能成为投稿成功的必需条件。字符子序列约束能限制删改，不能在文档里夸大为完整的语义真实性证明。

**完成证据：** 标题或地点命中现有拦截词也会被拦；演唱分类进入复审；数据库有原创声明；未配置真实 ASR 不会生成伪转写。答辩时能如实解释哪部分是规则、人工、真实服务或 Mock。

### P1-4：删除展品时清理语音回音文件

**事实依据：** ExhibitService.java:188 删除所有 echo 数据行，:190 只删除 exhibit.audioPath；没有遍历删除语音回音的 audioPath。用户先收到语音回音再删除展品，这些正常生成的文件会留在磁盘。

**修改方法：**

1. 删除前查出此展品下全部回音，收集非空音频路径；不能只查询 PASS，因为 REVIEW/REJECT 的语音同样已经落盘。
2. 数据库事务内删除关联记录，保留现有审核流水。
3. 数据库删除提交成功后删除展品及语音回音文件；直接使用 Spring 事务提交后回调即可，不增加后台任务系统。
4. 文件删除失败记日志，沿用现有清理方式，不为了本轮引入分布式事务。
5. 删除前的数量提示与实际含义一致：可显示公开回音数，但文字应说明该展品全部回音都会删除。

**完成证据：** 准备一件带文字、语音和待审语音回音的投稿，删除后数据库记录消失，各音频文件一起消失，审核流水仍在。

### P1-5：修正展品编号重用及正常多人投稿冲突

**事实依据：** ExhibitService.java:229 用“当前最大 no + 1”生成编号。删除编号最大的投稿后再投稿，会重用旧编号；两个正常用户同时提交也可能读到相同最大值，随后触发唯一约束。

**修改方法：**

- 改为数据库生成的单调序号或数据库序列，no 保持四位起步的展示格式，但允许位数自然增长。
- 序列初始值必须大于现有最大编号；已有编号和 URL 不重排，不删库重播种。
- 初始化与现有数据处理写明一次性 SQL/步骤即可，不为此引入迁移框架或反复启动修补机制。
- 不采用失败后无限重试、随机编号碰撞循环或全表加锁作为主要方案。

**完成证据：** 删除最大编号后新投稿不重用它；两个用户并行上传都成功，编号不同。

### P1-6：打捞去重必须区分对象类型

**事实依据：** DrawLog 已保存 targetType，但 DrawService.java:91 的 recentIds 只保留 targetId，:97 的抽取也只比较数字。exhibit 和 heritage 的自增 id 都会从 1 开始，现有种子即会产生相同数字；捞到历史声音 1 号会错误排除用户展品 1 号。

**修改方法：**

- 最近记录按 EXHIBIT/HERITAGE 分开取 ID，或使用由类型和 ID 组成的普通键；不需要计算哈希摘要。
- 继续保留“池子都抽过后放开”的现有行为。本轮不用另做抽卡算法。
- ApiSmokeTest 的 drawDoesNotRepeatImmediately 目前拼接两次抽取结果再比较两个组合，实际调用了四次，不能验证描述中的连续两次。改为一次请求得到一个 type + 对象标识后再比较，或在可控池子中做确定性测试。

**完成证据：** EXHIBIT:1 与 HERITAGE:1 是两个对象；一类的历史记录不能排除另一类。不要把现有“最近窗口去重”描述成严格的整轮无重复承诺。

### P1-7：真实内容与界面说明收尾

**事实依据：** 当前生成脚本产出合成信号；seed.json 虽然标注演示素材，历史区仍有“保存了 85 年”“磁带”“蜡筒”等真实史料式叙述。MineView/CollectionView 的全页文案又把全部用户数据、回音和音频都说成演示内容，新产生的真实投稿也被笼统包含。

**修改方法：**

1. 至少准备几件本人或队员授权录制的真实声音，使用实际日期、地点和故事，通过正式投稿流程入库。
2. 历史声音未取得可核实素材时，将具体记录明确标成“历史声音展位示例/合成演示”，同时改掉会让人误认为当前音频具有该历史来源的标题和说明；不得只去掉“非真实素材”标签。
3. 若换成真实历史音频，逐条登记来源页、音频对应关系和明确授权信息；未经核实不写“公有领域”。
4. 新素材的时长、波形和路径必须重新计算并同步数据库，不能只换 wav 文件却沿用旧 manifest。
5. 根据每条 seed/seeded 标记显示演示标识。真实投稿显示“用户投稿”，不再一概写“全部是演示用户”。
6. 本轮不要求新增素材后台 CRUD；通过受控导入或现有投稿即可。

**完成证据：** 真人录音播放内容与自己的故事对应；演示记录标识明确；历史来源字段与实际声音一致。

## 七、部署到服务器：采用一条可落地的路径

### 7.1 建议部署结构

采用单台 Linux 服务器：**Caddy 提供 HTTPS 和前端静态文件，Spring Boot 以 systemd 常驻，H2 文件库和音频目录固定在服务器磁盘。**

~~~text
电脑浏览器 / 手机浏览器 / 管理员浏览器
                 |
       https://你的实际域名
                 |
              Caddy
        /        |         \
   前端 dist   /api/*    /audio/*
                 |         |
           Spring Boot :8081
                 |
         H2 文件库 + 音频目录
~~~

H2 文件模式已经满足当前数据库要求。单实例运行，不让两份后端进程同时操作同一份数据。若课程另行指定 MySQL，再单独调整；本次不主动增加第二套数据库部署。

### 7.2 必须处理的具体问题

1. 现有 Vite dev/preview 绑定 127.0.0.1，只适合当前本地入口。把 host 改成 0.0.0.0 只能解决局域网开发访问，**不等于服务器部署完成**。
2. Vite 的 /api、/audio 代理不会跟着 dist 自动成为生产代理；生产站点必须配置真实反向代理。
3. router.js 使用 createWebHistory，刷新 /mine、/exhibit/编号、/admin 也要返回 index.html；API 和音频请求不能误回首页 HTML。
4. 外网浏览器录音需要 HTTPS 安全上下文和用户麦克风授权；不能只交一个 HTTP 公网 IP 然后发现“能看不能录”。依据：[MDN getUserMedia](https://developer.mozilla.org/en-US/docs/Web/API/MediaDevices/getUserMedia)。
5. npm run preview 是本地预览用途，正式部署提供 dist。依据：[Vite 部署说明](https://vite.dev/guide/static-deploy.html)。
6. 数据库与音频使用固定绝对目录，避免换一个工作目录启动后出现“库和音频都没了”的假象。
7. ADMIN_TOKEN 必须在服务器配置，否则现有过滤器会按设计关闭后台。真实密钥只放服务器环境文件。

### 7.3 给 DeepSeek 的部署文件要求

**实施顺序：**

6. 用真实 HTTPS 域名验证浏览、录音/文件上传、播放、复审、通知、编辑、删除。

8. 文档记录更新 jar/dist 的命令和停止服务后同时备份 data 目录的步骤；恢复也要同时恢复数据库与音频，不只复制一个数据库文件。

## 八、验收时怎样证明数据库真的变化

不要只给截图里的“提交成功”提示。准备三组独立浏览器会话：

- A：作者，保留自己的浏览器本地身份。
- B：听众，使用另一个浏览器、独立隐私窗口或另一台设备。
- C：管理员，进入 /admin。

同一浏览器同一站点的普通标签页共享 localStorage，通常不是两个独立用户。不要靠反复改昵称伪装为两个账号。当前轻身份不提供跨设备恢复同一身份，这一限制应在说明中写明，无须本轮新增邮箱密码。

### 8.1 一次连续演示

| 步骤 | 操作 | 老师应看到的结果 | 数据变化 |
| --- | --- | --- | --- |
| 1 | A 发布一件选择 SINGING 的合格投稿 | 作者页提示待复审，C 自动看到队列 | exhibit INSERT、audit_record INSERT |
| 2 | C 播放原声音并通过 | A 收到结果，公共馆藏出现 | exhibit 状态 UPDATE、audit_record 和 notification INSERT |
| 3 | B 打开该展品并发送文字回音 | B 看见明确结果，A 出现未读消息 | echo INSERT、notification INSERT |
| 4 | A 打开回音收件箱并标记已读 | 内容能定位到该展品，未读减少 | notification.readAt UPDATE |
| 5 | B 发送真实语音回音 | 可播放；若转写失败则 C 能听原音复审 | echo、音频文件、审核流水随结果变化 |

### 8.2 修改后必须新增的有意义验证

每项检查都要对应一个会改变实施结论的失败，不重复堆叠没有新信息的测试。

- 编辑：本人可改、他人不能改；id/no 不变、不增加投稿数；改完重审，未通过不进入公共查询。
- 通知：文字回音通过后作者收到；待审/拒绝不假装送达；人工通过后补送；刷新后存在；他人不能标记为自己的已读消息。
- 回音输入：失败保留内容；回车与点击不会在 busy 时重复提交；状态原因能显示。
- 复审音频：ASR 失败的原语音能在管理端播放并完成决定。
- 业务修复：删除关联音频、编号不复用、分类型打捞去重、同昵称不误判、演唱分类进复审。
- 部署：深层路由刷新、API 返回 JSON、音频可播放和拖动、HTTPS 麦克风、不同网络、重启后保留数据。

已有测试需要保持通过，但不要靠统一改成“都能通过”掩盖变化。例如 ASR 未配置转人工后，原有用 Mock 验证 PASS 的测试应明确限定在测试场景。

新机器构建流程须先准备测试音频：ApiSmokeTest 部分音频用例缺文件时会跳过，VoiceEchoAuditTest 直接读同一类文件还可能报错。本次本机 55 项都未跳过，不代表只 clone 代码后无需准备音频。
